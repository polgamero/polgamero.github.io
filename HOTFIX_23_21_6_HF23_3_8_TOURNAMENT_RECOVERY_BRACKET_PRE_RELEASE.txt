HOTFIX 23.21.6 HF23.3.8 — TOURNAMENT MULTI-TAB SAFETY + TAB-DURABLE SETTLEMENT RECOVERY
STATUS: PRE-RELEASE

ROOT CAUSE CONFIRMED
The released fixture called getTournamentState({resolveInterrupted:true}) on normal screen load. A second authenticated tab opening Tournament could therefore mutate the shared server run and convert the first tab's activeMatch to interrupted_match.

IMPLEMENTATION
1. ui.js normal load -> resolveInterrupted:false only.
2. js/tournamentRecovery.js stores activeMatch + pendingSettlement in sessionStorage (per-tab).
3. turnManager.js writes pendingSettlement before settlement callable; successful settlement clears pending + active markers.
4. main.js same-tab reload router retries pending settlement first. Only if no pending result exists, and the navigation is a true reload, may that tab request resolveInterrupted:true.
5. Explicit in-match forfeit clears markers after server confirmation; failure leaves them intact so the reload path can resolve safely.
6. If local initGame fails after the server already opened a tournament match, that same tab explicitly resolves the interruption to avoid a zombie run.
7. The fixture exposes a non-destructive recovery panel: pending settlement retry has precedence; orphan activeMatch resolution is manual + confirmed.

INVARIANTS
- Second-tab reads cannot mutate Tournament state.
- Pending terminal result always outranks interruption.
- No duplicate economic award: existing tournament receipt idempotency remains authoritative.
- No new server collection, Rules or callable.
- Between-match abandon and explicit in-match forfeit semantics remain unchanged.
